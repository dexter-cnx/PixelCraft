# PixelCraft Code Walkthrough

เอกสารนี้อธิบาย architecture ปัจจุบันของ PixelCraft ตั้งแต่เปิดแอป เลือกรูป ส่งงานผ่าน `flutter_rust_bridge` ไปยัง Rust, operation history, full-resolution export, transform tools, responsive editor และ workflow ของ Adjust/Creative Filters

> หลักการสำคัญคือ Flutter รับผิดชอบ UI และ state projection ส่วนงาน decode, filter, histogram, transform, operation replay และ export อยู่ใน Rust โดยงานหนักที่เรียกผ่าน synchronous FRB API ถูก dispatch ผ่าน background Dart isolate เพื่อลดการ block UI isolate

## Current flow summary

```text
Select image
  -> Rust load_image
  -> preview/original preview/histogram
  -> background prewarm of creative-filter thumbnails

Adjust slider
  -> drag: Flutter only
  -> release: background isolate -> Rust creates/replaces one draft Filter operation

Creative Filters
  -> thumbnails already cached from the current Apply checkpoint
  -> first tap: create one draft creative-filter operation at 1.0
  -> show intensity slider
  -> another filter/intensity: replace the same draft filter operation

Crop / Rotate / Flip / Straighten
  -> background isolate -> append draft transform operations

Apply
  -> bake every active draft operation into a new PNG checkpoint
  -> checkpoint becomes the new base/original for subsequent edits
  -> clear draft history and reset tool/filter selections
  -> prewarm creative-filter thumbnails once for the new base

Cancel
  -> restore the previous Apply checkpoint
  -> discard the entire draft branch
  -> keep the existing thumbnail cache because the base image did not change

Undo / Redo / Export
  -> background isolate -> synchronous FRB -> Rust operation engine
```

## Operation-based engine and Apply checkpoints

`rust/src/engine.rs` keeps original compressed bytes, a list of `EditOperation`, an active `cursor`, preview size settings, and temporary filter-transaction state. Preview and full-resolution export are generated by replaying active operations from the current checkpoint rather than by chaining stored PNG snapshots.

Supported operations include Filter, Crop, Rotate90, RotateDegrees/Straighten, FlipHorizontal, FlipVertical, and Resize. Undo decreases the cursor. Redo increases it. A new operation after Undo truncates the redo tail before appending the new operation.

Operations with `cursor > 0` are considered **unapplied draft edits**. Pressing Apply calls `apply_edits()`, renders the active operation list at full resolution, encodes that result as a lossless PNG, assigns it to `EngineState.original`, and clears operation history. The visible result therefore becomes the new editing base.

This means Apply is an explicit checkpoint boundary: subsequent filter previews and transforms start from the newly applied result rather than from the image imported at application startup.

## Flutter state and background processing

`lib/state/editor_controller.dart` projects the Rust engine state into Flutter. It tracks preview bytes, checkpoint preview, histogram, Adjust filter selection, creative filter selection/intensity, thumbnail cache, current tool, busy state, and session cursor values.

`EditorState.hasUnappliedEdits` is true when the Rust cursor is greater than zero. The shared Apply/Cancel action bar is enabled only while such draft operations exist.

`lib/core/image_engine.dart` wraps synchronous FRB calls and provides background helpers based on `Isolate.run()`. Heavy filter, transform, Apply, Cancel, Undo/Redo, preview generation, and export work therefore execute away from the UI isolate while Flutter remains responsible for local slider movement and rendering.

## Adjust controls

`FilterSlider` changes only its local thumb/value while the user drags. Rust is called once on `onChangeEnd`. This avoids processing brightness/contrast/saturation/blur/sharpen for every pointer event.

The first release creates one draft filter operation. Releasing the same Adjust slider again before Apply replaces that draft operation instead of stacking a second copy.

```text
Drag slider -> local Flutter state
Release -> commitFilterValue(finalValue)
        -> background isolate
        -> create or replace one Filter draft
        -> preview returned to Flutter

Apply -> bake draft as new checkpoint
Cancel -> discard draft and restore checkpoint
```

## Creative filter previews

Creative filters currently include grayscale, invert, vintage, oceanic, lofi, dramatic, golden, and pastel pink. There is no default selected creative filter.

Thumbnail generation starts automatically after the image finishes loading, before the user opens Filters. The source is the current Apply checkpoint preview. Opening Filters normally reuses the cached results and does not trigger regeneration after each filter tap.

`rust/src/api.rs::generate_filter_previews()` is optimized for browsing thumbnails:

1. decode the checkpoint source once,
2. resize it once to about 180 px max edge,
3. apply all creative filters from the same small base,
4. run variants in parallel with Rayon,
5. encode each result as PNG.

The thumbnails are intentionally stable while the user is browsing a draft. Trying Vintage and then Oceanic does not regenerate thumbnails and does not make Oceanic depend on the Vintage result.

After Apply changes the checkpoint, PixelCraft invalidates the old thumbnails and prewarms a new set in the background once. Cancel does not regenerate them because it restores the same checkpoint that produced the existing cache.

## Creative filter replacement and intensity

The first creative-filter tap creates one Filter draft at intensity `1.0` and shows a `0.0..1.0` intensity slider.

If the user then selects a different creative filter, or changes the intensity and releases the slider, PixelCraft replaces the active pending filter operation instead of stacking another filter on top. Internally the background task undoes that filter operation and commits the replacement from the same pre-filter checkpoint state.

For example, if the current Apply checkpoint is already Adjusted + Cropped:

```text
Checkpoint -> Vintage draft
```

switching to Oceanic becomes:

```text
Checkpoint -> Oceanic draft
```

not:

```text
Checkpoint -> Vintage -> Oceanic
```

The operation count therefore remains stable while the user browses creative filters or tunes intensity.

## Shared Apply / Cancel workflow

`EditorToolPanel` exposes one shared action bar for Adjust, Filters, Crop, and Rotate tools.

### Apply

`EditorController.applyEdits()` calls `ImageEngine.applyEditsInBackground()`. Rust renders all active draft operations at full resolution, stores the result as the new base image, clears operation history, resets selected filter/tool parameters, and starts thumbnail prewarming for the new checkpoint.

### Cancel

`EditorController.cancelEdits()` calls `ImageEngine.discardEditsInBackground()`. The background task rewinds the active operation cursor to the checkpoint and then calls `apply_edits()` on that unchanged checkpoint to clear the redo branch. Flutter resets filter and transform controls but keeps cached filter thumbnails because their source did not change.

The same Apply/Cancel semantics therefore cover filters and image transforms rather than having each tool commit permanently as soon as a control is touched.

## Transform tools

Crop uses normalized centered presets (1:1, 4:3, 3:4, 16:9, 9:16). Rotate supports quarter turns. Flip supports horizontal and vertical. Straighten uses -15°..15° and, like other sliders, processes only after release.

These transform operations remain draft edits until Apply is pressed. Cancel discards the entire set of transforms since the last checkpoint.

## Before / After

`original_preview()` produces a bounded preview from the current Apply checkpoint. Long press in the editor temporarily switches `visiblePreview` to that checkpoint image, so while draft edits are visible the user compares the draft against the last applied base.

## Full-resolution export

Export replays active operations from the current checkpoint at original resolution and supports PNG, JPEG quality, and WebP. `ExportFileService` saves to app documents and can invoke the system share sheet. Direct Android Gallery / iOS Photos insertion is not implemented yet.

Because active drafts are included in replay, export reflects the current visible edit state even before Apply. Apply is primarily the editing checkpoint/base promotion action rather than an export prerequisite.

## Responsive UI

`EditorScreen` uses a compact vertical layout on phones and a side tool panel from 900 px upward. `EditorToolPanel` exposes Adjust, Filters, Crop, Rotate, and Details. Editing tools share Cancel and Apply controls. Controls are temporarily disabled while a background operation is running.

## FRB code generation

The batch thumbnail API changes the Rust public API. Regenerate bridge files whenever `rust/src/api.rs` changes:

```bash
make codegen
```

The shared Cancel implementation itself reuses existing `undo`, `session_info`, and `apply_edits` FRB functions, so it does not introduce another generated Rust API method.

## Testing

Controller/widget tests cover commit-on-release Adjust behavior, replacement of the active draft filter, thumbnail prewarming, no default creative filter, cached thumbnails, creative-filter replacement, intensity replacement, shared Apply/Cancel checkpoints, transforms, undo/redo, and export. Golden baselines should be regenerated and reviewed whenever the tool action bar or Filters layout changes.
